Executive Summary

Max 200 words

V1 is a Python CLI tool that chains four external recon tools — subfinder, dnsx, httpx, katana — into one command against an authorized web scope, storing structured results in a local SQLite database and rendering a single self-contained, filterable HTML report. No hosted infrastructure, no queue system, no vulnerability scanning yet — those are deliberately deferred. The build is scoped tightly around what one person can ship correctly in ~56 hours: a stage pipeline (not a task queue), SQLite as the single queryable store with JSONL raw-capture for provenance, a transparent rule-based scoring engine (no ML yet), and a scope-allowlist enforced in code, not just documented. The report is the product's public face — it needs to look good enough to screenshot for a CV and be useful enough that you'd actually run it against your own bug bounty scope on a Tuesday night. Everything below is sized to be shippable in 3–4 weeks at 2 hrs/day, with explicit non-goals so scope doesn't quietly grow into a 3-month project.

No formal plugin system yet — the code is structured for one later, but building the abstraction now is premature.

Architecture & Module Layout

Execution model, folders, libraries
Decision — Stage Pipeline, Not a Queue

A simple in-process, mostly-linear stage pipeline: subfinder → dnsx → httpx → katana → prioritize, one Python process, in order. Parallelism within a stage is delegated to each Go tool's own concurrency flags (-c, -rl) rather than the orchestrator managing its own worker pool. A queue (Celery/RQ) earns its keep with multiple workers, cross-machine jobs, or durability across restarts — none of that applies to one person on one machine running jobs that finish in minutes. The ToolRunner abstraction (§06) is the seam that would let this migrate to a queue later without a rewrite, if it ever needed to.

Naming Note

httpx here is ProjectDiscovery's Go CLI probe, not the Python httpx HTTP client library. V1 never needs the Python library — probing, screenshots, and tech-detect are all delegated to the Go binary.

CLI Command Spec & Config Schema

Commands, flags, YAML files
terminal 
# core commands
reconctl init                         # scaffolds scope.yaml + config.yaml in cwd
reconctl doctor                       # checks required binaries + Chromium, prints versions
reconctl run --scope scope.yaml       # executes the full pipeline
reconctl report --run-id ID           # regenerate HTML report from existing DB (no rerun)
reconctl list-runs                    # table: id, target, started, duration, status
reconctl show --run-id ID             # CLI-only summary (counts, no HTML)
reconctl export --run-id ID --format json|csv --out FILE

# `run` flags
--scope PATH            required: path to scope.yaml
--config PATH            optional: defaults to ./config.yaml
--run-name TEXT           optional label for this run
--concurrency INT          default 20, passed to tools' -c flag
--rate-limit INT           default 10 req/s, passed to tools' -rl flag
--timeout INT              per-stage timeout in seconds, default 300
--no-screenshot            skip screenshot capture (avoids Chromium dep)
--stages TEXT              comma list, e.g. "subfinder,dnsx" — run a subset
--dry-run                  validate scope + config only, no network activity
-y, --yes                  skip the interactive scope-confirmation prompt
Design Note

scope.yaml and config.yaml are kept separate on purpose: the scope file is the authorization contract you review carefully and diff in git; it should never change just because you're tweaking concurrency.

scope.yaml — the authorization contract 
program_name: "example-corp-vdp"
authorization:
  authorized_by: "self"              # or: "bug-bounty-program", "signed-agreement"
  reference: "https://hackerone.com/example-corp"
  confirmed_on: "2026-08-08"
in_scope:
  domains:
    - "example.com"
    - "*.example.com"
out_of_scope:
  domains:
    - "blog.example.com"
  patterns:
    - "*.staging.example.com"
config.yaml — pipeline tuning 
run:
  concurrency: 20
  rate_limit_per_sec: 10
  timeout_seconds: 300
  retries: 1

    enabled: true
  http_probe:
    enabled: true

Data Model & Dedup/Scoring Strategy

SQLite schema, provenance, canonicalization
Decision — SQLite Is the Single Store

SQLite is the only queryable store: dedup checks, run history, cross-run diffing, and list-runs/show/export all need relational queries a directory of JSONL files can't serve without re-parsing everything. JSONL isn't a competing database — it's the raw-capture layer: every tool invocation writes its untouched JSONL output to disk before Python parses and inserts it into SQLite, giving an audit trail you can re-parse without re-running slower, network-touching tools.

schema.sql 
-- one row per pipeline execution
CREATE TABLE run (
  id INTEGER PRIMARY KEY,
  started_at TEXT, finished_at TEXT, status TEXT,
  scope_file_hash TEXT, config_hash TEXT, cli_args TEXT
);

-- one row per external tool invocation — THE provenance table
CREATE TABLE tool_result (
  id INTEGER PRIMARY KEY, run_id INTEGER, stage_name TEXT,
  tool_name TEXT, tool_version TEXT, command TEXT,
  exit_code INTEGER, started_at TEXT, finished_at TEXT,
  raw_output_path TEXT, item_count INTEGER, error_message TEXT
);

-- discovered subdomains; canonical_key is globally unique so first_seen_run_id works
CREATE TABLE asset (
  id INTEGER PRIMARY KEY, canonical_key TEXT UNIQUE,
  hostname TEXT, root_domain TEXT,
  first_seen_run_id INTEGER, source_tool_result_id INTEGER, created_at TEXT
);

CREATE TABLE dns_record (
  id INTEGER PRIMARY KEY, asset_id INTEGER, record_type TEXT,
  value TEXT, resolved_at TEXT, source_tool_result_id INTEGER
);

-- live HTTP(S) endpoints from httpx
CREATE TABLE endpoint (
  id INTEGER PRIMARY KEY, run_id INTEGER, asset_id INTEGER,
  url TEXT, dedup_key TEXT, status_code INTEGER, content_length INTEGER,
  title TEXT, tech_stack_json TEXT, screenshot_path TEXT,
  source_tool_result_id INTEGER, captured_at TEXT,
  UNIQUE(asset_id, dedup_key)
);

-- crawled URLs/endpoints from katana
CREATE TABLE url_item (
  id INTEGER PRIMARY KEY, run_id INTEGER, endpoint_id INTEGER,
  url TEXT, dedup_key TEXT, source_tool_result_id INTEGER, discovered_at TEXT
);

CREATE TABLE score (
  id INTEGER PRIMARY KEY, run_id INTEGER, endpoint_id INTEGER,
  score INTEGER, band TEXT, score_breakdown_json TEXT,
  rules_version TEXT, computed_at TEXT
);

-- generic attachment table: screenshots, header dumps, response snippets
CREATE TABLE evidence (
  id INTEGER PRIMARY KEY, related_table TEXT, related_id INTEGER,
  evidence_type TEXT, file_path TEXT, sha256 TEXT, created_at TEXT
);
Provenance Rule

Every "finding" row (asset, endpoint, url_item) carries a source_tool_result_id foreign key. Any UI element can answer "which tool, which run, when" with one join.

Single-Writer Discipline

External tools only write JSONL to disk — they never touch SQLite directly. Only the main Python process writes to the DB, single-threaded, after parsing. This sidesteps SQLite's concurrent-writer footguns entirely.

Dedup / canonicalization rules

  • Hostnames: lowercase, strip trailing dot, strip default ports before hashing → canonical_key. Unique globally, not per-run, so first_seen_run_id is meaningful and the V1.1 diff feature is a single query, not new infrastructure.
  • URLs: lowercase scheme+host (path case preserved), strip default ports, normalize trailing slash, sort query params for dedup_key, ignore #fragment. Original url kept as-is for display.
  • Endpoints: unique per run on (asset_id, dedup_key).
  • Evidence: optionally content-addressed by sha256 to skip re-storing identical screenshots on reruns — nice-to-have.
Scoring signalWeight
Title/body contains admin / login / dashboard / manage keywords+30
Interesting path (api, internal, staging, backup, test, debug) + 200 + non-trivial length+20
Tech fingerprint matches a static known-outdated list (live CVE lookup is V1.1)+15
Status 401/403 — protected resource, worth noting+10
Content-length 0 or matches a generic/parking-page heuristic−10

Bucketed into Critical / High / Medium / Low / Info. score_breakdown_json stores which rules fired, so the report can show why — an engineering-quality signal and a strong interview talking point.

Tool Integration Plan

V1 toolset only — 4 tools + 1 pure-Python stage

Shared pattern: a ToolRunner class implements timeout + retry + tool_result logging once; each stage supplies a binary name, an argument builder, and a parser. This is the seam that becomes a real plugin system in V1.1/V2 without building the abstraction now.

subfinder

Stage 1 · Subdomain enum
InputRoot domains from scope.yaml (wildcard prefixes stripped)
Invocationsubfinder -d <domain> -silent -oJ -o out.jsonl
OutputJSONL: {host, input, source[]}
ParserStream JSONL → asset rows
Timeout / retry180s default, 1 retry, 2s backoff
Failure isolationMarks tool_result.status = failed, run continues — partial output still usable since subfinder streams as it goes

dnsx

Stage 2 · DNS resolve
InputHostnames from subfinder + seed domains
Invocationdnsx -l hosts.txt -silent -json -resp -a -aaaa -cname -o out.jsonl
OutputJSONL with resolved A/AAAA/CNAME records
Parser→ dns_record rows; flags "resolvable" assets
Timeout / retry60s default, 1 retry
Failure isolationIf dnsx fails entirely, fall back to unfiltered subfinder hosts rather than aborting

httpx

Stage 3 · Probe + screenshot
InputResolved hostnames
Invocationhttpx -l hosts.txt -silent -json -title -tech-detect -status-code -content-length -screenshot -srd ./screenshots -o out.jsonl
OutputJSONL: url, status, title, tech[], content-length, screenshot path
Parser→ endpoint rows + evidence rows (verify file exists, sha256)
Timeout / retry600s default; hosts chunked into batches to stay boundable/resumable
Failure isolationScreenshot failure (commonly: missing Chromium) auto-retries once without -screenshot

katana

Stage 4 · URL collection
InputLive (200/30x) endpoints from httpx as crawl seeds
Invocationkatana -u seeds.txt -silent -jc -d 2 -rl <rate> -j -o out.jsonl
OutputJSONL of discovered URLs, JS files, forms
Parser→ url_item rows linked to originating endpoint_id
Timeout / retry900s / max_crawl_time, no auto-retry — partial crawl logged as partial
Failure isolationTotal failure leaves url_item empty; report renders "no data collected," rest stays intact
Default choice, explained: katana (active, shallow crawl) beats gau (passive/archive-only) as the V1 default because it surfaces real, currently-live endpoints — more useful for "Interesting Endpoints" — and the target is already authorized, so light active crawling is acceptable. gau stays a reasonable lower-footprint alternative for a future --passive-only flag.

prioritize

Stage 5 · Pure Python, no external tool
Inputendpoint + url_item rows for the run
Outputscore rows
Timeout / retryN/A — deterministic, in-process, fast
Failure isolationWrapped per-row: a malformed row logs a warning and scores as Info rather than aborting the pass

Static, portable, client-side filtering
Design Decision

The report is one static, portable HTML file — all CSS/JS inlined, no CDN, no server. Filtering, sorting, and search run entirely client-side against a JSON blob embedded in the page. Worth stating in interviews: the report is safe to hand to someone offline, no server required.

README Policy Text

Authorized-use — ready to paste
SECURITY.md 
## Authorized Use Only

This tool performs active reconnaissance against network targets (DNS
resolution, HTTP requests, light web crawling). It must only be run
against systems you own, or systems you have explicit written
authorization to test (e.g., a signed engagement letter, or a bug
bounty program's published scope).

Running this tool against systems without authorization may violate
the Computer Fraud and Abuse Act (US), the Computer Misuse Act (UK),
or equivalent laws in your jurisdiction. You are solely responsible
for confirming authorization before every run.

## Scope Allowlist

Every run requires a scope.yaml file declaring the authorized
target(s) and an authorization block recording who authorized the
engagement and a reference to that authorization (a program URL or
signed document). The tool enforces this allowlist in code — any
host resolved outside the declared in_scope patterns, or matching
an out_of_scope pattern, is excluded before any active stage runs.
By default, the CLI shows you the resolved scope and asks for
confirmation before the first network request; pass --yes only
once you're confident in an unattended run.

## Safe Defaults and Rate Limiting

Concurrency and request-rate defaults are intentionally conservative
(20 concurrent connections, 10 requests/second) to minimize impact on
target infrastructure. Increase these only against targets where
you've confirmed higher load is acceptable.

## Audit Trail

Every tool invocation is logged to the local SQLite database with its
exact command, timestamps, and exit status, and every scope
inclusion/exclusion decision is logged to the per-run log file. Run
history is queryable at any time via reconctl list-runs. This audit
trail is local-only — nothing is transmitted off your machine.

CV Bullets & Interview Prep

CV bullets

  • Designed and built a Python CLI recon pipeline orchestrating 4 chained security tools (subfinder, dnsx, httpx, katana) with SQLite-backed provenance tracking, deduplication, and a rule-based prioritization engine, generating a self-contained, filterable HTML report.
  • Engineered a subprocess orchestration layer with per-stage timeout, retry, and failure-isolation logic, ensuring a single tool crash never aborts an entire recon run.
  • Implemented hostname/URL canonicalization and dedup logic enabling reliable cross-run "new since last scan" detection with no external infrastructure.
  • Built a transparent, rule-based endpoint scoring engine with an inspectable score breakdown — prioritizing explainability over a black-box number — surfaced directly in the generated report.
  • Shipped a fully local-first security tool (SQLite + static HTML, no server, no cloud) with scope-allowlist enforcement built into the code as a runtime safety guardrail, not just documentation.

Interview talking points

  • Why a stage pipeline, not a task queue: solo/local scale doesn't justify Redis + worker infrastructure; the ToolRunner abstraction is the seam that would let this migrate to a queue later without a rewrite, if it ever needed to.
  • Why SQLite and JSONL, not one or the other: SQLite is the single queryable store; JSONL is the untouched raw-capture layer that makes provenance auditable and lets you re-parse without re-running network-touching tools.
  • Why katana over gau by default: live, currently-real endpoints are more useful for a report meant to prioritize action, and the target is already authorized so light active crawling is acceptable — explain the tradeoff, don't pretend it's the only right answer.
  • How scope safety is enforced, not just documented: the allowlist check runs in code before any active stage, with an interactive confirmation gate by default — point at the exact function that makes an out-of-scope run fail closed.
  • What was deliberately deferred and why: nuclei, ML scoring, and a plugin system were all cut from V1 on purpose — scoping discipline is itself the signal a hiring manager is often testing for.
